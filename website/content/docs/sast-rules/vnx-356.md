title: "VNX-356 – Electron app silently grants permissions or accepts invalid certificates"
description: "Reports Electron main-process code that answers a security prompt for the user: permission request/check handlers that always grant, certificate-error handlers that always accept, a certificate verifier that always returns 0, and the ignore-certificate-errors switch."
---

## Overview

VNX-356 maps to [CWE-356: Product UI does not Warn User of Unsafe Actions](https://cwe.mitre.org/data/definitions/356.html). In an Electron app, the main process decides whether the user is ever asked about a dangerous action. This rule reports JavaScript/TypeScript code that makes that decision for the user with an unconditional "yes":

1. `session.setPermissionRequestHandler(...)` whose handler calls its callback with `true` unconditionally (camera, microphone, geolocation, notifications and every other permission are granted with no prompt).
2. `setPermissionCheckHandler(...)` whose handler returns `true` unconditionally.
3. `app.on('certificate-error', ...)` / `webContents.on('certificate-error', ...)` whose handler calls its callback with `true` unconditionally.
4. `setCertificateVerifyProc(...)` whose handler calls its callback with `0` (trusted) unconditionally.
5. `app.commandLine.appendSwitch('ignore-certificate-errors')`, unless it sits in a development-only branch (`!app.isPackaged`, `isDev`, `NODE_ENV === 'development'`) within the three lines above.

A handler whose body (followed up to eight lines) contains a condition, ternary, comparison, allowlist lookup or `switch` is a decision and is not reported, nor is a callback given `false`, nor are test files, comments and string literals. Web confirmation dialogs are not judged: whether an action deserves a prompt is a design question that no line of code answers.

**Severity:** Low | **CWE:** [CWE-356](https://cwe.mitre.org/data/definitions/356.html) | **Languages:** node

## Why This Matters

Browsers warn before a site gets the camera or before loading a page with a bad certificate. An Electron app that grants or accepts everything removes that warning, so a compromised or injected page in the app's window gets device access, and a network attacker can intercept TLS without the user ever seeing an error.

## What Gets Flagged

```javascript
// FLAGGED
session.defaultSession.setPermissionRequestHandler((webContents, permission, callback) => {
  callback(true);
});

app.on('certificate-error', (event, webContents, url, error, certificate, callback) => {
  event.preventDefault();
  callback(true);
});

app.commandLine.appendSwitch('ignore-certificate-errors');
```

```javascript
// NOT FLAGGED: grants only named permissions to the app's own origin
session.defaultSession.setPermissionRequestHandler((webContents, permission, callback) => {
  const origin = new URL(webContents.getURL()).origin;
  callback(origin === 'https://app.example.com' && ALLOWED.has(permission));
});
```

## Remediation

1. Grant only the permissions the app needs, and only to origins it trusts; deny everything else (`callback(false)`).
2. Never accept a certificate error unconditionally. If an internal host must be trusted, pin its certificate fingerprint and check the URL.
3. Remove `ignore-certificate-errors` from production builds.
