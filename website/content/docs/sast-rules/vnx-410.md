## Overview

VNX-410 maps to [CWE-410: Insufficient Resource Pool](https://cwe.mitre.org/data/definitions/410.html). The rule reports a shared server resource pool (database connections, request threads, a request executor) capped at one or two members by a literal.

**Severity:** Low | **CWE:** [CWE-410](https://cwe.mitre.org/data/definitions/410.html) | **Languages:** java

## Why This Matters

When a pool has one or two members, a couple of slow or deliberately held requests take all of them, and every other client blocks until they are released. Whether a larger literal is enough for peak load cannot be judged statically, so only the degenerate sizes are reported.

## What Gets Flagged

```java
config.setMaximumPoolSize(1);                                    // FLAGGED (HikariCP)
ds.setMaxTotal( 2 );                                             // FLAGGED (DBCP)
QueuedThreadPool threads = new QueuedThreadPool(2);              // FLAGGED (Jetty)
private final ExecutorService pool = Executors.newFixedThreadPool(1);   // FLAGGED in a ServerSocket/servlet/controller file
```

```properties
spring.datasource.hikari.maximum-pool-size=1                     # FLAGGED
server.tomcat.threads.max = 2                                    # FLAGGED
```

Not flagged: sizes from variables or expressions, larger literals, `newScheduledThreadPool(1)` and `newSingleThreadExecutor()`, a one-thread executor in code that does not serve requests, test files, comments and strings.

## Remediation

1. Size pools for peak concurrency, from configuration rather than a literal.
2. Set an acquisition timeout so a starved pool fails fast instead of queueing forever.
3. For confirmed false positives, add a `// vulnetix-ignore: VNX-410` comment on the line.
