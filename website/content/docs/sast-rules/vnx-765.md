title: "VNX-765 – Lock Released Twice"
description: "Reports a Go mutex or Java lock released a second time without being re-acquired: two unlocks in one block, an unlock in a try block repeated in its finally, and a Go explicit Unlock in a function that already defers it."
---

## Overview

VNX-765 maps to [CWE-765: Multiple Unlocks of a Critical Resource](https://cwe.mitre.org/data/definitions/765.html). It reports two `unlock()`/`Unlock()`/`RUnlock()` statements on the same lock in one block with no re-acquisition in between, a Java `unlock()` inside a `try` block (including on an early-return branch) whose `finally` unlocks again, and a Go explicit `Unlock()` in a function that already has `defer mu.Unlock()` and does not re-lock afterwards.

It does not report an unlock on an early-exit branch followed by the main unlock outside it, unlock/wait/lock sequences, `switch` cases or `if`/`else` branches that each release once, different locks, releases inside a goroutine or lambda, or test files.

**Severity:** Low | **CWE:** [CWE-765](https://cwe.mitre.org/data/definitions/765.html) | **Languages:** java, go

## Why This Matters

Java's `ReentrantLock.unlock()` throws `IllegalMonitorStateException` when the lock is not held, so the second release replaces the method's result with an exception. Go's `sync.Mutex` aborts the whole program with `fatal error: sync: unlock of unlocked mutex`, which cannot be recovered.

## What Gets Flagged

```java
lock.lock();
try {
    if (items.isEmpty()) {
        lock.unlock();
        return null;
    }
    return items.remove(0);
} finally {
    lock.unlock();     // flagged
}
```

```go
q.mu.Lock()
defer q.mu.Unlock()
if len(q.items) == 0 {
    q.mu.Unlock()      // flagged
    return 0, false
}
```

## Remediation

1. Release in exactly one place: the `finally` block in Java, a single `defer` in Go.
2. If a function must release early, do not also defer the release.
