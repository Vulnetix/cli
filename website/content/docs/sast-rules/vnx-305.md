---
title: "VNX-305 – Authentication Bypass by Primary Weakness"
description: "An auth middleware, decorator, permission class or servlet filter that lets a request through because a token, API key or Authorization header is present, without verifying it."
---

## Overview

VNX-305 maps to [CWE-305: Authentication Bypass by Primary Weakness](https://cwe.mitre.org/data/definitions/305.html). It reports an authentication check that only tests whether a credential exists. A Node/Express middleware, a Python decorator, view or Django REST Framework permission, or a Java servlet filter or Spring interceptor reads a token, API key, `Authorization` header or session cookie from the request and then grants access (`next()`, `return f(*args, **kwargs)`, `call_next`, `chain.doFilter(...)`, or `return True`/`true` from an auth or permission method) when the value is merely non-empty, or as the very next statement after rejecting an empty one.

Not reported: a check whose condition or intervening lines verify, decode, validate, compare or look the credential up; a variable assigned from a verification call; a value held in the server-side session store (`req.session.user`, `session.getAttribute`), which the server itself put there at login; client-side route guards such as Angular `canActivate`; test files and comments. Verification hidden in another function between the read and the grant is not followed.

**Severity:** High | **CWE:** [CWE-305](https://cwe.mitre.org/data/definitions/305.html) | **Languages:** java, node, python

## Why This Matters

The authentication scheme may be sound (signed JWTs, opaque API keys), but if the gate only checks that a header is present, any value authenticates. An attacker sends `Authorization: Bearer x` and reaches every protected route.

## What Gets Flagged

```javascript
// FLAGGED
const token = req.headers.authorization?.split(' ')[1];
if (token) return next();

if (!sessionToken) { return res.status(401).send('login required'); }
next();
```

```python
# FLAGGED
token = request.headers.get("Authorization", "").replace("Bearer ", "")
if token:
    return f(*args, **kwargs)

# FLAGGED: a DRF permission that returns the presence test
def has_permission(self, request, view):
    return bool(request.headers.get("Authorization"))
```

```java
// FLAGGED
String authToken = request.getHeader("Authorization");
if (authToken != null && authToken.startsWith("Bearer ")) {
    chain.doFilter(req, res);
```

Not flagged: `req.user = jwt.verify(token, secret); next();`, `if token and ApiToken.query.filter_by(value=token).first():`, `if (req.session.user) next();`.

## Remediation

1. Verify the credential before granting access: check a JWT's signature, issuer, audience and expiry, or look an API key up in a store and compare it in constant time.
2. Attach the verified identity to the request (`req.user`, `g.user`) and authorise from that, never from the raw header.
3. Fail closed: any error during verification must reject the request.
