## Overview

VNX-832 maps to [CWE-832: Unlock of a Resource that is not Locked](https://cwe.mitre.org/data/definitions/832.html). It reports the release line in these shapes:

- **Java** (`java.util.concurrent` locks, including `rw.readLock()`/`writeLock()`):
  1. `unlock()` of a lock whose `tryLock()`/`tryLock(timeout)` result was discarded as a bare statement in the 40 lines above;
  2. `unlock()` in a `finally` block whose `try` acquires the same lock with `lockInterruptibly()` or `tryLock()`, so an interrupt, a failed `tryLock` or the early return after it still reaches the unlock;
  3. `unlock()` of a lock field or variable the file declares but never acquires and never passes to other code.
- **Python** (`threading`): `release()` after a bare `acquire(blocking=False)`, `acquire(False)` or `acquire(timeout=...)` whose result was discarded.
- **C/C++** (pthreads): `pthread_mutex_unlock`/`pthread_rwlock_unlock` after a bare `pthread_mutex_trylock`, `pthread_mutex_timedlock` or `pthread_rwlock_try*lock`/`timed*lock` whose return value was discarded. C++: `m.unlock()` after a bare `m.try_lock()`, `try_lock_for()` or `try_lock_until()` whose result was discarded.

Not reported: `lock()` before `try` with `unlock()` in `finally`; `if (lock.tryLock()) { try ... finally unlock }`; an unlock guarded by an `if` on the same or the preceding line (`if (acquired)`, `isHeldByCurrentThread()`); a `tryLock`/`acquire` whose result is assigned or tested; blocking acquisition; begin/end method pairs in the same file; lock parameters, locks handed to another object or returned from a getter; comments and string literals. Double unlocks are VNX-765.

**Severity:** Low | **CWE:** [CWE-832](https://cwe.mitre.org/data/definitions/832.html) | **Languages:** java, python, c, cpp

## Why This Matters

Releasing a lock the thread does not hold throws `IllegalMonitorStateException` in Java (often from a `finally`, where it replaces the original exception), raises `RuntimeError` in Python, and is undefined behaviour for a default pthread mutex. Worse, the code between the failed acquisition and the release ran without the lock, so the data it protects was modified concurrently.

## What Gets Flagged

```java
lock.tryLock();
try {
    reload();
} finally {
    lock.unlock();              // FLAGGED: tryLock() result ignored
}

try {
    lock.lockInterruptibly();
    data.put(k, v);
} finally {
    lock.unlock();              // FLAGGED: interrupt before acquisition still unlocks
}
```

```python
self.lock.acquire(blocking=False)
try:
    self._tick()
finally:
    self.lock.release()         # FLAGGED
```

## Remediation

1. Acquire before `try`: `lock.lock(); try { ... } finally { lock.unlock(); }`.
2. Test the result of non-blocking or timed acquisition and release only when it succeeded: `if (lock.tryLock()) { try { ... } finally { lock.unlock(); } }`.
3. In Python prefer `with lock:`; in C check `pthread_mutex_trylock(&m) == 0` before unlocking.
