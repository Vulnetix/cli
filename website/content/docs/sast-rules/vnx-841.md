---

## Overview

VNX-841 maps to [CWE-841: Improper Enforcement of Behavioral Workflow](https://cwe.mitre.org/data/definitions/841.html). A multi-step process (pay, then ship; apply, then approve) is only enforced if the server decides when a step has happened. Two shapes are reported:

1. **A workflow-state field set from a request value**, directly or through one assignment: `order.status = req.body.status`, `.update(status=request.POST["status"])`, `loan.setStatus(...)` with a `@RequestParam` value, `order.is_paid` / `.approved` / `.verified` / `.payment_status` from the request. `status`, `stage`, `step`, `state` and `completed` count only on a workflow object (order, payment, checkout, booking, loan, application, ticket, transfer and similar).
2. **An `if` that advances the workflow because the request says so**, such as `if request.args.get("payment_status") == "success"` or `if (req.query.paid === 'true')`, followed within six lines by a status change, `setStatus`, or a `fulfil`/`ship`/`approve`/`capture` call.

**Severity:** Medium | **CWE:** [CWE-841](https://cwe.mitre.org/data/definitions/841.html) | **Languages:** java, node, python

## Why This Matters

A client that can set the next state can skip the step in between: it can mark an unpaid order paid by calling the return URL with `?paid=true`, or approve its own application.

## What Gets Flagged

```typescript
// FLAGGED: the redirect's query string decides the order is paid
if (req.query.paid === 'true') {
  checkout.status = 'complete';
  await fulfil(checkout);
}
```

```java
// FLAGGED: the client picks the order's next state
order.setStatus(request.getParameter("status"));
```

Not flagged: state set from a constant after a server-side check (`stripe.checkout.sessions.retrieve(...)`, a verified webhook), a requested transition checked against an allowed-transitions table, handlers behind an admin or role check or under an admin path, response status codes, a profile `status` or an address `state`.

## Remediation

1. Decide each transition on the server from verified facts: query the payment provider, or act on a signed webhook.
2. Model the workflow as a state machine and reject a requested transition that is not allowed from the current state.
3. Restrict manual state changes to authorised roles.
