title: "VNX-920 – Improper Restriction of Power Consumption"
description: "Reports an Android WakeLock or WifiLock acquired with acquire() and no timeout, in Java and Kotlin."
---

## Overview

An Android `PowerManager.WakeLock` or `WifiManager.WifiLock` is acquired with `acquire()` and no timeout. If the release is skipped (an exception, an early return, a killed callback) the device stays awake, or the Wi-Fi radio stays on, until the process dies. The rule reports `X.acquire()` where `X` is declared as a WakeLock/WifiLock or assigned from `newWakeLock()`/`createWifiLock()` in the same file, a chained `newWakeLock(...).acquire()`, and a bare `acquire()` inside a Kotlin `apply { }` opened on a `newWakeLock` line.

**Severity:** Medium | **CWE:** [CWE-920](https://cwe.mitre.org/data/definitions/920.html) | **Languages:** java, kotlin

## Why This Matters

A leaked wake lock drains the battery in hours and Android may restrict or flag the app for excessive wake-ups.

## What Gets Flagged

```java
pm.newWakeLock(PowerManager.FULL_WAKE_LOCK, "acme:play").acquire();
wakeLock.acquire();
```

```kotlin
pm.newWakeLock(PowerManager.PARTIAL_WAKE_LOCK, "acme:sync").apply {
    acquire()
}
```

Not flagged: `acquire(timeout)`, `acquire()` on semaphores, locks and pools, test files, comments and strings. Whether a `release()` follows is not judged; Android lint's WakelockTimeout check applies the same standard.

## Remediation

Pass a timeout (`acquire(10 * 60 * 1000L)`) and release in a `finally` block, or use WorkManager, which manages wake locks for you.
