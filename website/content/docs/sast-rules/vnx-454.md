## Overview

VNX-454 maps to [CWE-454: External Initialization of Trusted Variables or Data Stores](https://cwe.mitre.org/data/definitions/454.html). It reports Python web code that initialises authorisation state from values the client controls: a cookie or header whose key names a privilege or authentication state (admin, is_admin, role, permissions, logged_in, X-User-Role...), a query or form parameter with such a key tested in an `if`, a session key of that kind assigned from request data, and a trust-flag variable (is_admin, g.authenticated) assigned from a cookie, header or query parameter, directly or through a variable a few lines above. Server-side state (request.user, current_user, session.get, a database user), lookalike keys such as admin_email, and settings read from os.environ are not reported.

**Severity:** Medium | **CWE:** [CWE-454](https://cwe.mitre.org/data/definitions/454.html) | **Languages:** python

## Why This Matters

A privilege the client can set is a privilege the client can grant itself: sending `Cookie: admin=1` or `X-User-Role: admin` is enough to pass the check.

## What Gets Flagged

```python
# FLAGGED: privilege read from a cookie
if request.COOKIES.get("admin") == "1":
    return render(request, "admin.html")

# FLAGGED: session role set from the request
session["role"] = request.form["role"]

# NOT FLAGGED: privilege taken from the authenticated user
if request.user.is_staff:
    ...
```

## Remediation

1. Derive privileges from server-side state: the authenticated user record, a signed session written by the server, or a permission lookup.
2. Never trust a cookie, header or parameter that names a role or flag; treat it as a request, not a fact.
3. For confirmed false positives, add a `# vulnetix-ignore: VNX-454` comment on the line.
