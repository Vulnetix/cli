title: "VNX-413 – Improper Resource Locking"
description: "Java code that may run without the lock it needs or cannot release it: a bare tryLock() whose result is discarded, synchronized (new ...), and Lock.lock()/lockInterruptibly() whose unlock in the same method is not in a finally block or that is never unlocked."
---

## Overview

VNX-413 maps to [CWE-413: Improper Resource Locking](https://cwe.mitre.org/data/definitions/413.html). The rule reports Java code that believes it holds exclusive access but may not, or that cannot reliably give it up.

**Severity:** Low | **CWE:** [CWE-413](https://cwe.mitre.org/data/definitions/413.html) | **Languages:** java

## Why This Matters

A discarded `tryLock()` result means the critical section runs whether or not the lock was obtained. `synchronized (new Object())` excludes nobody. A lock released only on the success path stays held after an exception, and every later caller blocks.

## What Gets Flagged

```java
exportLock.tryLock();                 // FLAGGED: result discarded
synchronized (new Object()) { ... }   // FLAGGED: no shared monitor

lock.lock();                          // FLAGGED: unlock below is not in finally
value = Math.addExact(value, by);
lock.unlock();

rw.readLock().lock();                 // FLAGGED: never unlocked
return items.get(key);
```

Not flagged: `lock.lock(); try { ... } finally { lock.unlock(); }`, `if (lock.tryLock(...))` or an assigned tryLock result, a lock taken in one method and released in another (acquire/close pairs), `lock()` on types that are not java.util.concurrent locks, test files, comments and strings.

## Remediation

1. Always pair `lock()` with `try { ... } finally { lock.unlock(); }` placed immediately after it.
2. Branch on the result of `tryLock()`.
3. Synchronize on a private final field shared by every caller.
4. For confirmed false positives, add a `// vulnetix-ignore: VNX-413` comment on the line.
