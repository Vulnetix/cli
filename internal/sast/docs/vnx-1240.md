## Overview

VNX-1240 maps to [CWE-1240: Use of a Cryptographic Primitive with a Risky Implementation](https://cwe.mitre.org/data/definitions/1240.html).

**Severity:** Medium | **CWE:** [CWE-1240](https://cwe.mitre.org/data/definitions/1240.html) | **Languages:** java

## Why This Matters

ECB encrypts each block independently, so equal plaintext blocks give equal ciphertext blocks. The structure of the data shows through the encryption, and an attacker can cut, replay and reorder blocks without knowing the key. In Java, asking for a bare algorithm name such as `"AES"` selects ECB through the provider default, so the mode is often chosen by accident.

## What Gets Flagged

Most ECB in Java is reported by [VNX-CRYPTO-003](../vnx-crypto-003/) (AES in ECB mode, CWE-327): an explicit `/ECB/` transformation, a bare block-cipher name such as `"AES"` whose provider default is ECB, a constant or a `getProperty` default holding one, and a call split after `getInstance(`. This rule does not report those calls again, so a Java ECB cipher is one finding. It reports the forms VNX-CRYPTO-003 does not:

```java
Cipher cipher = Cipher.getInstance(alg + "/ECB/PKCS5Padding");   // mode concatenated on

String t = conf.getOrDefault("vault.cipher", "AES/ECB/PKCS5Padding");
Cipher c = Cipher.getInstance(t);                                // getOrDefault default

// src/test/java/...: ECB in test sources, which VNX-CRYPTO-003 leaves out
Cipher fixture = Cipher.getInstance("AES/ECB/PKCS5Padding");
```

Not flagged: `"AES/GCM/NoPadding"`, `"RSA/ECB/OAEPWithSHA-256AndMGF1Padding"` (RSA has no chaining), `KeyGenerator.getInstance("AES")`, `new SecretKeySpec(raw, "AES")`, and `Cipher.getInstance("AES/ECB/PKCS5Padding")` in production code, which VNX-CRYPTO-003 reports.

## Remediation

1. Use an authenticated mode: `Cipher.getInstance("AES/GCM/NoPadding")` with a fresh 12-byte IV for every encryption.
2. Always spell out the full transformation; never rely on the provider default.
