---
title: "VNX-609 – Double-Checked Locking"
description: "Reports Java double-checked lazy initialisation (check, synchronized, same check) on a field of the same file that is not declared volatile."
---

## Overview

VNX-609 maps to [CWE-609: Double-Checked Locking](https://cwe.mitre.org/data/definitions/609.html). It reports a `synchronized (...)` block immediately preceded by `if (x == null)`, `if (null == x)` or `if (!flag)` and whose first statement repeats the same check, where `x` is a field declared in the same file without `volatile`.

Not reported: a `volatile` field, the local-variable idiom (`Helper h = helper; if (h == null) ...`) over a volatile field, a single check inside a synchronized method or block, `AtomicReference` checks, the holder-class idiom, and fields declared in another file.

**Severity:** Low | **CWE:** [CWE-609](https://cwe.mitre.org/data/definitions/609.html) | **Languages:** java

## Why This Matters

Without `volatile`, the Java memory model lets another thread see the reference assigned before the constructor's writes are visible, so it uses a half-built object; with a boolean flag it can see the flag set before the data the flag guards.

## What Gets Flagged

```java
private static Registry instance;

if (instance == null) {
    synchronized (Registry.class) {      // flagged
        if (instance == null) {
            instance = new Registry();
```

## Remediation

1. Declare the field `volatile`.
2. Or use the initialisation-on-demand holder class, an `enum` singleton, or eager initialisation.
3. For a confirmed false positive, add a `// vulnetix-ignore: VNX-609` comment on the line.
