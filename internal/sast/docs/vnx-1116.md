description: "A Python docstring that documents a parameter the function does not take, usually left behind by a rename or removal."
---

## Overview

VNX-1116 maps to [CWE-1116: Inaccurate Source Code Comments](https://cwe.mitre.org/data/definitions/1116.html). It reports a Python docstring entry (Google-style `Args:`/`Parameters:` or Sphinx `:param name:`) naming a parameter that is not in the function's signature.

**Severity:** Low | **CWE:** [CWE-1116](https://cwe.mitre.org/data/definitions/1116.html) | **Languages:** Python

## Why This Matters

A docstring that describes a parameter the function no longer takes is evidence that the comment and the code have drifted apart. Readers trust the comment, so they pass an argument that is ignored or misread what the function checks. The same drift often hides changed behaviour around validation or access control.

## What Gets Flagged

Reported at the docstring line that names the stale parameter:

```python
def load_user(db, user_id):
    """Load a user.

    Args:
        db: Database handle.
        userid: The user's primary key.      # FLAGGED: no parameter 'userid'
    """
```

```python
def write_blob(path, data):
    """Write bytes to disk.

    :param path: destination file
    :param verbose: print progress            # FLAGGED: no parameter 'verbose'
    """
```

## What Does Not Get Flagged

- Functions that take `**kwargs`, whose keyword arguments are legitimately documented by name.
- `*args`/`**kwargs` entries, description continuation lines, and `Returns`/`Raises`/`Yields` sections.
- NumPy-style dashed sections (not parsed).
- Test files.

## Remediation

1. Rename the docstring entry to match the parameter, or remove it if the parameter is gone.
2. Re-read the rest of the docstring: a stale parameter is often a sign the described behaviour changed too.
