---
title: "VNX-924 – Improper Enforcement of Message Integrity During Transmission in a Communication Channel"
description: "Reports Java code that opens a plain TCP socket or listener to a non-loopback peer without TLS, so the bytes can be altered in transit."
---

## Overview

Java code opens a raw TCP connection or listener with no TLS: `new Socket(host, port)`, `new ServerSocket(port)`, `connect(new InetSocketAddress(...))` on a plain socket, `SocketChannel.open(new InetSocketAddress(...))`, and `createSocket`/`createServerSocket` on the non-TLS `SocketFactory.getDefault()`/`ServerSocketFactory.getDefault()`.

**Severity:** Medium | **CWE:** [CWE-924](https://cwe.mitre.org/data/definitions/924.html) | **Languages:** java

## Why This Matters

Anyone on the network path can change (or read) what is sent, and neither end can tell.

## What Gets Flagged

```java
ServerSocket server = new ServerSocket(9000);
try (Socket s = new Socket(host, port)) {
Socket t = SocketFactory.getDefault().createSocket(host, 7002);
```

Not flagged: `SSLSocketFactory`/`SSLServerSocketFactory` sockets, a plain socket the same file upgrades with `createSocket(plain, host, port, true)` (STARTTLS), loopback peers and bindings, `new Socket(proxy)`, the `Socket` type in declarations, test files, comments and strings. Whether the protocol on top adds its own MAC or signature is not judged.

## Remediation

Use `SSLSocketFactory.getDefault()` / `SSLServerSocketFactory.getDefault()` (or an `SSLContext` you configure) with hostname verification, or a protocol library that runs over TLS.
