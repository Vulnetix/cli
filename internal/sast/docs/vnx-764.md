title: "VNX-764 – Lock Acquired Again While Held"
description: "Reports a Go mutex or Java lock acquired a second time in the same or a nested block while the first acquisition is still held: Go Lock/RLock twice (deadlock), Java ReentrantLock lock() twice and read-to-write lock upgrade."
---

## Overview

VNX-764 maps to [CWE-764: Multiple Locks of a Critical Resource](https://cwe.mitre.org/data/definitions/764.html). It reports a second acquisition of the same lock, in the same block or one nested inside it, with no release of that lock in between. In Go, any `Lock()` or `RLock()` after a `Lock()`/`RLock()` on the same receiver deadlocks (a deferred `Unlock` runs too late). In Java, `lock()`/`lockInterruptibly()` twice on a `ReentrantLock` leaves a hold count the single `unlock()` does not clear, and `readLock().lock()` followed by `writeLock().lock()` deadlocks.

It does not report acquisitions with a release in between, sibling `if`/`else` branches, acquisitions inside a goroutine, lambda or anonymous class, different locks, `tryLock()`, Java write-to-read downgrade, or test files. Locks reached through a helper call are not followed.

**Severity:** Low | **CWE:** [CWE-764](https://cwe.mitre.org/data/definitions/764.html) | **Languages:** java, go

## Why This Matters

A non-reentrant lock taken twice by the same goroutine never returns. A reentrant lock taken twice and released once stays held after the method returns, so every other thread blocks forever.

## What Gets Flagged

```go
s.mu.RLock()
v, ok := s.m[k]
if !ok {
    s.mu.Lock()        // flagged: RWMutex cannot be upgraded
```

```java
rw.readLock().lock();
try {
    if (v == null) {
        rw.writeLock().lock();   // flagged
```

## Remediation

1. Release the lock before taking it again, or restructure so the critical section takes it once.
2. For read-then-write, release the read lock, take the write lock and re-check the condition.
